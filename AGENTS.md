# Robyn repository guide

Robyn combines Rust in `src/` with the Python package in `robyn/`, tests in `unit_tests/` and `integration_tests/`, and documentation in `docs_src/`. Native-extension changes must preserve the Python API and supported interpreter compatibility.

Use stable Rust/Cargo, a native compiler, and a Python environment in the supported 3.9–3.13 range. From the repository root, the documented development path is `poetry install --with dev --with test`, then `poetry run maturin develop` to build the extension into that environment. Run `poetry run pytest unit_tests` for the unit suite or `poetry run pytest integration_tests` for the integration suite; `poetry run pytest` runs both. For an authorized development server, `poetry run test_server` uses the built extension and starts the integration example. Follow the checked-in metadata/lockfiles when resolving dependencies rather than combining incompatible setup examples. Rust CI runs `cargo check`, `cargo test`, `cargo fmt --check`, and `cargo clippy`. Python CI uses Nox; with Python 3.12 and Nox available, `nox --non-interactive --error-on-missing-interpreter -p 3.12` selects that interpreter. Inspect `noxfile.py` first: its test session exports `requirements.txt`, builds wheels into `dist/`, and on macOS adds Rust targets before the universal build. Those generated files and toolchain changes are setup effects, not instruction edits. Choose the affected suite and report missing interpreter/toolchain prerequisites explicitly.

`integration_tests/conftest.py` starts and stops real test subprocesses on ports 8080/8081; some fixtures bind a network interface. Don't start a second test server by analogy with a README example or run against a production listener. Nox lint sessions may rewrite files, so inspect the session before running it. A Rust build does not validate the Python import, HTTP/WebSocket behavior, or shutdown lifecycle; relevant native changes need the built extension and focused Python tests. Benchmarks, preview deployments, and releases are separate from ordinary checks.

## Completing work

Carry the authorized change through the relevant checks and repair failures it causes. Make routine, reversible implementation choices using existing patterns; ask only when missing information, a material product decision, or an authorization boundary prevents the next step. Existing authorization remains valid within its scope. If blocked, name the exact action and missing prerequisite, retain concise evidence, and continue independent work.

Choose verification proportional to the change. For instructions or prose, inspect changed paths, links, and local instruction precedence and run `git diff --check -- <changed-paths>`; don't install dependencies or run the application solely for a prose edit unless an existing mandatory gate requires setup. For behavior changes, exercise the affected behavior and applicable checks below, then broaden only for failures or unresolved risk. Report files changed, checks actually run and their results, commands only inspected, and remaining limitations. A build or source inspection alone does not prove runtime behavior. Continue through already-authorized follow-through; stop at explicit review checkpoints or boundaries requiring new authorization.
